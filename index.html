I bo'lim: Asoslar

Docker — bu nima?

Konspekt Lectrum «Docker» intensivi (4 ta dars) asosida + qo'shimcha izohlar bilan.

Ta'rif: Docker — ilovani va unga kerak bo'lgan hamma narsani (kutubxonalar, sozlamalar, runtime) bitta yengil konteynerga joylab, uni istalgan kompyuterda bir xil ishga tushirish platformasi.

Oddiy qilib aytganda: dastur o'zining «chamadoni» bilan keladi. Chamadonni qayerda ochsang ham, ichidagi narsalar bir xil.

Nega kerak bo'ldi?

Mashhur muammo: «Mening kompyuterimda ishlayapti-ku!» Dasturchida Node 18, serverda Node 12; kutubxona versiyalari boshqa; OT boshqa. Natijada bir joyda ishlaydi, boshqa joyda buziladi.

Docker bu muammoni hal qiladi: muhit ham kod bilan birga «qadoqlanadi». Xuddi dengizdagi standart konteynerlar kabi: ichida nima borligidan qat'i nazar, kran, kema va poyezd uni bir xil usulda ko'taradi.

Docker ≠ Virtual mashina

Kursdagi asosiy g'oya: VM — apparat (hardware) darajasidagi virtualizatsiya, Docker — operatsion tizim darajasidagi virtualizatsiya. VM har biri uchun to'liq «mehmon OT» yuklaydi, konteynerlar esa bitta host yadrosini (kernel) bo'lishib ishlatadi.

VM'da har ilova o'z OT'ini ko'tarib yuradi (GB'lab), konteynerda esa yo'q (MB'lab).

Virtual mashinaDocker konteyner
HajmiGigabaytlarMegabaytlar (alpine ≈ 5 MB)
Ishga tushishiDaqiqalarSoniyalar, hatto millisekundlar
OTHar birida to'liq mehmon OTHost yadrosini bo'lishadi
IzolyatsiyaJuda kuchli (alohida yadro)Kuchli, lekin yadro umumiy
Bitta serverdaO'nlabYuzlab, minglab

Qisqa tarix

  • 2013 — Solomon Hykes (dotCloud) Docker'ni ochiq kod qilib chiqardi.
  • Avval LXC (LinuX Containers) ustida ishlagan, keyin o'zining libcontainer → runC dvigateliga o'tdi.
  • 2015 — OCI (Open Container Initiative) standarti tuzildi.
  • Bugun: Docker Desktop (Windows / macOS / Linux), Docker Hub — dunyodagi eng katta image ombori.
Eslab qol:
konteyner — bu kichik VM emas, bu izolyatsiya qilingan oddiy jarayon (process)!
I bo'lim: Asoslar

Docker qanday ishlaydi?

Butun jarayon uch so'zdan iborat: Dockerfile → Image → Container.

Oshxona misoli: Dockerfile — retsept, Image — muzlatilgan tayyor ovqat, Container — isitib dasturxonga qo'yilgani.

Dockerfile

Image qanday yig'ilishini qadamma-qadam yozadigan oddiy matn fayli: qaysi bazadan boshlash, nima o'rnatish, qaysi fayllarni nusxalash.

Image (obraz)

Konteyner uchun read-only shablon. Qatlamlardan iborat. Teg (tag) bilan versiyalanadi: nginx:1.16.0, alpine:3.9.

Container

Image'ning ishga tushirilgan nusxasi. Uni yaratish, to'xtatish, qayta ishga tushirish va o'chirish mumkin.

Registry

Image'lar ombori. Ommaviy — Docker Hub; shaxsiy — registry:2, GitHub/GitLab Registry.

Qatlamli fayl tizimi (UFS)

Union File System — bir necha qatlamni (layer) ustma-ust qo'yib, ularni bitta fayl tizimidek ko'rsatadi. Dockerfile'dagi har bir RUN, COPY, ADD buyrug'i yangi qatlam hosil qiladi. Konteyner ishga tushganda, ustiga bitta yoziladigan yupqa qatlam qo'shiladi.

  • Bir xil qatlamlar qayta ishlatiladi: 10 ta konteyner bitta nginx image'ni diskda bitta nusxada bo'lishadi.
  • Build keshlanadi: faqat o'zgargan qatlamdan boshlab qayta yig'iladi. Shuning uchun kam o'zgaradigan buyruqlarni tepaga yoz!
  • Konteyner o'chirilsa, uning R/W qatlami ham yo'qoladi → muhim ma'lumot uchun volume kerak (4-varaq).

Izolyatsiya «sehri»: Linux yadrosining ikki quroli

Namespaces — konteyner nimani ko'rishini cheklaydi. Har biri o'zini serverda yolg'izdek his qiladi:

  • pid — jarayonlar, net — tarmoq
  • mnt — fayl tizimi, uts — hostname
  • ipc — jarayonlararo aloqa, user — foydalanuvchilar

cgroups (control groups) — konteyner qancha resurs ishlatishini cheklaydi: CPU, RAM, disk I/O, jarayonlar soni.

docker run -d -m 10m \
  --memory-reservation 5m nginx
Windows / macOS'da Docker Desktop yashirin kichik Linux VM (WSL2) ichida ishlaydi, chunki konteynerga Linux yadrosi kerak.
I bo'lim: Asoslar

Docker arxitekturasi

Docker mijoz–server (client–server) modelida qurilgan. Sen terminalda yozgan docker buyrug'i o'zi hech narsa qilmaydi — u faqat daemon'ga REST API orqali «buyurtma» yuboradi.

Mijoz va host bitta kompyuterda ham, turli joyda ham bo'lishi mumkin (masalan, DOCKER_HOST=ssh://server).

Qismlar birma-bir

QismVazifasi
docker (CLI)Mijoz. Buyruqlaringni REST API so'roviga aylantirib, daemon'ga yuboradi (Unix socket /var/run/docker.sock yoki TCP orqali).
dockerdDocker Daemon — fonda ishlaydigan server. Image, konteyner, tarmoq va volume'larni boshqaradi, build qiladi, registry bilan gaplashadi.
containerdKonteynerlarning hayot siklini boshqaruvchi runtime: image'ni tortish, saqlash, konteynerni yaratish/to'xtatish. Kubernetes ham uni ishlatadi.
runcEng pastki daraja (OCI runtime). Yadroga murojaat qilib namespaces va cgroups bilan jarayonni ishga tushiradi, keyin chetga chiqadi.
containerd-shimHar bir konteynerning «enagasi»: daemon qayta ishga tushsa ham konteyner o'lmaydi.
Docker EngineYuqoridagilarning hammasi birgalikda: daemon + API + CLI.
RegistryImage'lar ombori: Docker Hub, shaxsiy registry, GHCR, ECR va boshqalar.

?docker run -d -p 80:80 nginx yozganda nima bo'ladi

  1. CLI buyruqni JSON so'rovga aylantirib, dockerd'ga yuboradi.
  2. Daemon nginx:latest image'i lokal diskda bormi, tekshiradi.
  3. Yo'q bo'lsa — Docker Hub'dan qatlamma-qatlam pull qiladi.
  4. containerd image asosida konteyner yaratadi: ustiga R/W qatlam, tarmoq interfeysi, IP manzil.
  5. runc namespaces va cgroups'ni sozlab, nginx jarayonini PID 1 sifatida ishga tushiradi.
  6. Host'dagi 80-port konteynerning 80-portiga ulanadi (-p host:konteyner).
  7. -d tufayli konteyner fonda qoladi, terminalga uning ID'si chiqadi.

II bo'lim: Konteyner ichidan

Konteyner anatomiyasi

Konteyner — bu «quti» emas. Bu Linux'dagi oddiy jarayon (process), uning atrofiga esa bir nechta «devor» va «o'lchagich» o'rnatilgan. Keling, uni bo'laklarga ajratamiz.

Markazda doim bitta jarayon turadi. Qolgan hammasi uning atrofidagi «muhit».

QismNima uQayerda ko'rinadi
RootfsKonteyner «/» deb ko'radigan fayl tizimi: image qatlamlari + ustidagi yoziladigan qatlamdocker diff, .GraphDriver
JarayonCmd/Entrypoint'dan ishga tushgan dastur, konteyner ichida PID 1docker top
NamespacesIzolyatsiya: o'z PID'lari, tarmog'i, hostname'i, mount'lari/proc/<pid>/ns
cgroupsLimitlar: RAM, CPU, jarayonlar soni, disk I/O/sys/fs/cgroup, docker stats
Tarmoqveth interfeysi, IP, /etc/hosts, /etc/resolv.conf, hostname.NetworkSettings
MountsTashqaridan ulangan papkalar va /proc, /sys, /dev.Mounts
KonfiguratsiyaEnv, Cmd, Entrypoint, WorkingDir, User, Labels, portlar.Config, .HostConfig
XavfsizlikCapabilities, seccomp profili, AppArmor/SELinux.HostConfig.CapAdd
Metama'lumot64 belgili ID, nom, yaratilgan vaqt, holat, log faylidocker inspect

Konteyner ID va nomi

  • ID — 64 ta o'n oltilik belgi (sha256 uzunligida): 3f9a1c7d2e…. Odatda birinchi 12 tasi ko'rsatiladi, buyruqlarda esa 3–4 ta belgi ham yetadi, agar takrorlanmasa.
  • Nom — --name bilan beriladi. Berilmasa, Docker kulgili nom to'qiydi: sleepy_turing, brave_hopper. Nom yagona bo'lishi shart.
  • Hostname — konteyner ichida standart holatda qisqa ID'ga teng.

Image va konteyner farqi

  • Image — sinf (class), konteyner — ob'ekt (instance).
  • Image o'zgarmaydi; konteyner o'zgaradi (fayl yozadi, jarayonlari bor).
  • Bitta image'dan istalgancha konteyner yaratish mumkin.
  • Image o'chirilishi uchun undan yasalgan konteynerlar avval o'chirilishi kerak.
Konteyner vaqtinchalik (ephemeral) bo'lishi kerak: uni istalgan payt o'chirib, yangisini ko'tarsang, hech narsa yo'qolmasin!
II bo'lim: Konteyner ichidan

Image ichki tuzilishi (OCI)

Image — bu bitta fayl emas. U JSON hujjatlar va tar arxivlar to'plami bo'lib, hammasi o'z sha256 xeshi bo'yicha saqlanadi. Bu format OCI Image Spec standartida yozilgan.

Docker pull qilganda avval index, keyin sening protsessoringga mos manifest, keyin config va qatlamlar yuklanadi.

Image Index

«Ko'p platformali» ro'yxat: har bir arxitektura (amd64, arm64, …) uchun alohida manifestga havola. Shuning uchun nginx ham noutbukda, ham Raspberry Pi'da ishlaydi.

Manifest

Bitta platforma uchun: config faylining xeshi va qatlamlar xeshlari ro'yxati (tartibi muhim!).

Config

Image'ning «pasporti»: Env, Cmd, Entrypoint, WorkingDir, ExposedPorts, User, Labels, qatlamlar tarixi (history).

Qatlamlar (layers)

Har biri — fayl tizimi o'zgarishlarining tar.gz arxivi. O'chirilgan fayllar maxsus «whiteout» fayl bilan belgilanadi.

Config JSON qanday ko'rinadi (qisqartirilgan)

{
  "architecture": "amd64",  "os": "linux",
  "config": {
    "Env": ["PATH=/usr/local/sbin:/usr/bin", "NGINX_VERSION=1.27.0"],
    "Entrypoint": ["/docker-entrypoint.sh"],
    "Cmd": ["nginx", "-g", "daemon off;"],
    "ExposedPorts": { "80/tcp": {} },
    "StopSignal": "SIGQUIT"
  },
  "rootfs": {
    "type": "layers",
    "diff_ids": ["sha256:9a1c…", "sha256:4b7e…", "sha256:c02f…"]
  },
  "history": [ { "created_by": "ADD alpine-minirootfs.tar.gz / " }, … ]
}

Digest va teg farqi

  • Teg (nginx:1.27) — o'zgaruvchan yorliq. Bugun bir image'ni, ertaga boshqasini ko'rsatishi mumkin.
  • Digest (nginx@sha256:5f3b…) — o'zgarmas. Mazmun bir bayt o'zgarsa, digest ham o'zgaradi.
  • Ishlab chiqarishda (production) aniq versiya yoki digest bilan ishlash xavfsizroq.
docker image inspect nginx:alpine --format "{{json .RootFS.Layers}}"
docker buildx imagetools inspect nginx:alpine   # index va platformalar
docker image ls --digests
docker save nginx:alpine -o n.tar && tar -tf n.tar  # ichidagi blob'larni ko'rish
OCI'da 3 ta standart bor: Image Spec (image formati), Runtime Spec (konteyner qanday ishga tushadi, runc shuni bajaradi) va Distribution Spec (registry API).
II bo'lim: Konteyner ichidan

Diskdagi tuzilma: overlay2

Qatlamlarni bitta fayl tizimiga «yopishtiradigan» mexanizm — storage driver. Linux'da standart driver — overlay2 (yadrodagi OverlayFS asosida).

  • lowerdir — image qatlamlari, faqat o'qiladi.
  • upperdir — konteynerning yoziladigan qatlami. Yangi va o'zgargan fayllar shu yerga tushadi.
  • workdir — OverlayFS'ning ichki ishchi papkasi (o'zgarishlarni xavfsiz yozish uchun).
  • merged — hammasi birlashgan ko'rinish. Konteyner uchun / shu.

Uch holat

O'qish

Fayl yuqoridan pastga qidiriladi va birinchi topilgani ko'rsatiladi. Nusxa olinmaydi, shuning uchun tez.

O'zgartirish

Copy-on-Write: fayl avval butunlay upperdir'ga ko'chiriladi, keyin o'zgartiriladi. Katta faylda 1 bayt o'zgarsa ham butun fayl ko'chadi!

O'chirish

Pastdagi fayl haqiqatda o'chmaydi. Upperdir'da whiteout (maxsus 0/0 qurilma fayli) yaratiladi va fayl «yashiriladi».

Xulosa: RUN rm katta.zip alohida qatlamda bo'lsa, image kichraymaydi! O'chirishni yuklab olish bilan bitta RUN ichida qil.

/var/lib/docker ichida nima bor

/var/lib/docker/
├── overlay2/            # qatlamlar
│   ├── 3f9a…/diff/      # qatlam mazmuni
│   ├── 3f9a…/link       # qisqa nom (l/ papkasidagi symlink)
│   ├── 3f9a…/lower      # pastdagi qatlamlar ro'yxati
│   ├── 3f9a…/work/      # workdir
│   ├── 3f9a…/merged/    # faqat konteyner ishlayotganda
│   └── l/
├── image/overlay2/      # imagedb (config'lar), layerdb (qatlamlar zanjiri)
├── containers/<id>/
│   ├── config.v2.json   # Config, holat, nom
│   ├── hostconfig.json  # portlar, limitlar, mounts, restart
│   ├── hostname  hosts  resolv.conf
│   └── <id>-json.log    # docker logs shu fayldan o'qiydi
├── volumes/<nom>/_data # nomli volume'lar
├── network/             # tarmoqlar bazasi
└── buildkit/            # build keshi
docker info --format "{{.Driver}}"          # overlay2
docker inspect lab --format "{{json .GraphDriver.Data}}"
# → LowerDir, UpperDir, WorkDir, MergedDir yo'llari
Diqqat: yangi Docker versiyalarida containerd image store yoqilgan bo'lishi mumkin. Unda qatlamlar /var/lib/containerd ichida saqlanadi. Docker Desktop'da esa bu papkalar yashirin Linux VM ichida bo'ladi.

Qo'lda o'zgartirma! /var/lib/docker ichini faqat o'rganish uchun ko'r, tahrirlash Docker'ni buzadi.

Namespaces batafsil

Namespace — Linux yadrosining xususiyati: u jarayonga tizim resurslarining alohida nusxasini ko'rsatadi. Jarayon o'zini tizimda yolg'izdek his qiladi.

NamespaceNimani ajratadiDocker'da
pidJarayon raqamlari. Konteyner ichida birinchi jarayon — PID 1Doim (--pid=host bilan o'chiriladi)
netTarmoq interfeyslari, IP, marshrutlar, portlar, iptablesDoim (--network host bundan mustasno)
mntMount nuqtalari, ya'ni fayl tizimi ko'rinishiDoim
utsHostname va domen nomiDoim (--hostname)
ipcUmumiy xotira, semaforlar, xabar navbatlariDoim (--ipc)
userUID/GID: ichkaridagi root tashqarida oddiy foydalanuvchi bo'ladiFaqat userns-remap yoki rootless rejimda

PID namespace: bir jarayon, ikki raqam

O'zing tekshirib ko'r

docker run -d --name lab nginx:alpine
PID=$(docker inspect -f "{{.State.Pid}}" lab)   # host'dagi PID, masalan 4321
sudo ls -l /proc/$PID/ns                  # net:[4026532608] pid:[4026532606] …
sudo lsns -p $PID                         # qaysi namespace'larda
sudo nsenter -t $PID -n ip addr           # konteyner tarmog'iga host'dan "kirish"
docker exec lab ps                        # ichkarida: PID 1 = nginx

Namespace'larni bo'lishish

  • --network container:lab — boshqa konteyner tarmog'iga qo'shilish (Kubernetes pod'lari aynan shunday: bitta IP, bir necha konteyner).
  • --pid container:lab — boshqa konteyner jarayonlarini ko'rish (debug uchun qulay).
  • --network host, --pid host — izolyatsiyani o'chirish. Faqat nima qilayotganingni bilsang ishlat.
Docker exec ham shu yo'l bilan ishlaydi: yangi jarayon ishlab turgan konteynerning namespace'lari ichiga «kiritiladi» (setns).
II bo'lim: Konteyner ichidan

cgroups batafsil

Namespaces «nimani ko'rish»ni cheklasa, cgroups «qancha ishlatish»ni cheklaydi. Limit bo'lmasa, bitta konteyner butun serverning RAM'ini yeb qo'yishi mumkin.

cpu.max = 50000 100000 degani: har 100 ms ichida 50 ms protsessor vaqti = yarim yadro.

Bayroqcgroup fayliMa'nosi
-m 64mmemory.maxRAM'ning qattiq chegarasi
--memory-reservation 32mmemory.lowYumshoq chegara: RAM tanqisligida shu darajagacha siqiladi
--memory-swap 128mmemory.swap.maxRAM + swap jami (−1 = cheksiz)
--cpus 1.5cpu.maxKo'pi bilan 1,5 yadro
--cpu-shares 512cpu.weightNisbiy ulush: faqat raqobat bo'lganda ta'sir qiladi
--cpuset-cpus 0,1cpuset.cpusFaqat 0 va 1-yadrolarda ishlash
--pids-limit 100pids.maxJarayonlar soni (fork-bomba himoyasi)
--device-write-bpsio.maxDiskka yozish tezligi chegarasi

OOM (Out Of Memory) bo'lsa nima bo'ladi?

  1. Jarayon memory.maxdan ko'p xotira so'raydi.
  2. Yadro avval keshni tozalab ko'radi.
  3. Yetmasa, OOM killer konteyner ichidagi jarayonni SIGKILL bilan o'ldiradi.
  4. Konteyner exit 137 bilan to'xtaydi, .State.OOMKilled = true.
docker run -d --name lab -m 64m --cpus 0.5 --pids-limit 100 nginx:alpine
docker stats --no-stream lab     # MEM USAGE / LIMIT: 3.1MiB / 64MiB
docker update --memory 128m --memory-swap 256m lab   # to'xtatmasdan o'zgartirish
docker inspect -f "{{.State.OOMKilled}}" lab
Limitsiz konteyner = serverdagi hamma narsa uchun xavf. Productionda doim -m va --cpus qo'y!

pause buyrug'i ham cgroups orqali ishlaydi: freezer jarayonlarni «muzlatib» qo'yadi, ular xotirada qoladi, lekin CPU ishlatmaydi.

cgroups v1 da har bir resurs alohida daraxtda edi. v2 da yagona daraxt; zamonaviy distributivlarda standart holatda v2 ishlatiladi.

II bo'lim: Konteyner ichidan

Konteyner tarmog'i ichidan

Standart bridge tarmog'ida har bir konteyner host'ga virtual «kabel» orqali ulanadi. Bu kabel veth pair deyiladi: bir uchi konteyner ichida, ikkinchisi host'da.

Chiquvchi trafik

Konteyner internetga chiqqanda iptables MASQUERADE qoidasi manbani host IP'siga almashtiradi (NAT). Tashqi dunyo faqat host'ni ko'radi.

Kiruvchi trafik (-p)

-p 8080:80 host'ning 8080-portiga kelgan paketni DNAT qoidasi bilan 172.17.0.2:80ga yo'naltiradi. Yordamchi docker-proxy jarayoni ham ishga tushadi.

Ichki DNS

O'zing yaratgan tarmoqda konteynerlar bir-birini nomi bilan topadi: ping db. Buni 127.0.0.11 dagi ichki DNS qiladi. Standart bridgeda bu ishlamaydi!

Konteyner ichidagi tarmoq fayllari

  • /etc/hostname — konteyner nomi (qisqa ID).
  • /etc/hosts — o'z IP'si va --add-host bilan qo'shilgan yozuvlar.
  • /etc/resolv.conf — DNS server manzili (host'dan yoki 127.0.0.11).

Bu uch fayl image'da yo'q. Docker ularni ishga tushirish paytida containers/<id>/ papkasidan bind mount qiladi.

ip addr show docker0                          # host'dagi ko'prik
bridge link                                   # qaysi veth'lar ulangan
sudo iptables -t nat -L DOCKER -n             # -p uchun DNAT qoidalari
docker exec lab cat /etc/resolv.conf
docker network inspect bridge --format "{{json .IPAM.Config}}"
Port «bandmi?» xatosi: bind: address already in use — host'dagi o'sha port boshqa dastur yoki boshqa konteyner tomonidan band.
II bo'lim: Konteyner ichidan

PID 1 va signallar

Konteyner PID 1 jarayoni tirik ekan tirik bo'ladi. PID 1 tugasa, konteyner ham to'xtaydi. Shuning uchun konteyner ichida nginx daemon off; bilan (oldingi rejimda) ishlaydi.

docker stop qanday ishlaydi

Kutish vaqtini o'zgartirish: docker stop -t 30 lab; signalni Dockerfile'dagi STOPSIGNAL almashtiradi.

Shell forma va exec forma

Yomon (shell forma):

CMD node server.js
# aslida: /bin/sh -c "node server.js"
# PID 1 = sh, node esa uning bolasi

Yaxshi (exec forma):

CMD ["node", "server.js"]
# PID 1 = node, signallarni
# to'g'ridan-to'g'ri oladi

PID 1 ning uch xususiyati

  1. Standart signal ishlovchilari yo'q. Oddiy jarayon SIGTERM'da o'ladi, PID 1 esa uni o'zi ushlamasa e'tiborsiz qoldiradi.
  2. Zombi jarayonlarni «ko'mish» (reaping) uning vazifasi. Dastur buni qilmasa, zombi jarayonlar to'planib qoladi.
  3. U o'lsa — hammasi o'ladi. Konteynerdagi qolgan jarayonlar ham SIGKILL oladi.

Yechim: docker run --init. Bu PID 1 sifatida kichik tini init jarayonini qo'yadi: u signallarni uzatadi va zombilarni tozalaydi.

ENTRYPOINT + CMD birgalikda

ENTRYPOINT ["/docker-entrypoint.sh"]     # doim ishlaydi
CMD ["nginx", "-g", "daemon off;"]       # entrypoint'ga argument
# natija: /docker-entrypoint.sh nginx -g "daemon off;"
# skript oxirida:  exec "$@"   ← PID 1 ni nginx'ga topshiradi!
docker run …Nima ishga tushadi
docker run imgENTRYPOINT + CMD
docker run img shENTRYPOINT + sh (CMD almashtirildi)
--entrypoint sh imgFaqat sh (ENTRYPOINT almashtirildi, CMD tashlab yuboriladi)

Restart siyosatlari

no

Standart. O'zi qayta ko'tarilmaydi.

on-failure[:5]

Faqat exit kodi 0 bo'lmasa, 5 martagacha qayta urinadi.

always

Doim qayta ko'taradi, daemon qayta yoqilganda ham.

unless-stopped

always kabi, lekin qo'lda to'xtatilgan bo'lsa, qayta yoqilmaydi. Serverlar uchun eng qulayi.

Qayta urinishlar orasidagi kutish vaqti har safar ikki barobar oshadi (100 ms, 200 ms, 400 ms …), shunda to'xtovsiz qulayotgan konteyner serverni band qilmaydi.

Loglar qayerga ketadi

Docker konteynerning stdout va stderr oqimlarini ushlab, log drayverga beradi. Standart drayver — json-file. U cheklanmasa, disk to'lib qolishi mumkin!

docker run -d --log-opt max-size=10m --log-opt max-file=3 nginx
docker logs --since 10m --tail 100 -f lab
Shuning uchun kursda nginx loglari ln -sf /dev/stdout /var/log/nginx/access.log bilan konsolga yo'naltirilgan edi!
II bo'lim: Konteyner ichidan

Xavfsizlik qatlamlari

Konteynerlar host yadrosini bo'lishadi, shuning uchun himoya bir necha qavatdan iborat. Piyoz kabi: bittasi yorilsa, keyingisi ushlab qoladi.

Capabilities: root'ni bo'laklarga ajratish

Linux'da root'ning kuchi ~40 ta alohida capabilityga bo'lingan. Docker standart holatda faqat 14 tasini qoldiradi: CHOWN, DAC_OVERRIDE, FOWNER, FSETID, KILL, SETGID, SETUID, SETPCAP, NET_BIND_SERVICE, NET_RAW, SYS_CHROOT, MKNOD, AUDIT_WRITE, SETFCAP. Masalan, SYS_ADMIN (mount va boshqalar) yo'q.

docker run --cap-drop ALL --cap-add NET_BIND_SERVICE myapp   # minimal huquq

Seccomp

Standart profil xavfli tizim chaqiruvlarini (syscall) bloklaydi: reboot, kexec_load, mount va boshqalar.

AppArmor / SELinux

Yadro darajasida fayl va resurslarga kirish qoidalari. Ubuntu'da docker-default AppArmor profili.

User namespace

userns-remap yoki rootless rejim: ichkaridagi root host'da huquqsiz foydalanuvchi bo'ladi.

Read-only rootfs

--read-only --tmpfs /tmp: hujumchi fayl yozib qo'ya olmaydi.

Xavfsiz ishga tushirish namunasi

docker run -d --name api \
  --user 1000:1000 \
  --read-only --tmpfs /tmp \
  --cap-drop ALL \
  --security-opt no-new-privileges \
  -m 256m --cpus 1 --pids-limit 200 \
  myname/api:1.4.2

Hech qachon qilma

  • -v /var/run/docker.sock:/var/run/docker.sock ni ishonchsiz konteynerga berish. Bu host'da root degani.
  • Sababsiz --privileged.
  • Parol va kalitlarni ENV yoki image ichiga yozish. Ular docker history va inspectda ko'rinadi. Build uchun RUN --mount=type=secret ishlat.
  • Noma'lum muallifning image'ini tekshirmasdan ishlatish. docker scout cves bilan tekshir.

Amaliyot: konteynerni ochib ko'ramiz

O'rganganlarimizni bitta konteynerda qadamma-qadam tekshiramiz. Linux host kerak; Docker Desktop'da /proc va /var/lib/docker qadamlari VM ichida bo'ladi.

1.Ishga tushiramiz

docker run -d --name lab -m 64m --cpus 0.5 -p 8080:80 nginx:alpine
curl -I localhost:8080          # HTTP/1.1 200 OK

2.Jarayonlar (PID namespace)

docker top lab                  # host ko'radigan PID'lar: 4321, 4350…
docker exec lab ps              # ichkarida: 1 nginx: master, 7 nginx: worker

3.Hostname va tarmoq (uts, net)

docker exec lab hostname        # 3f9a1c7d2e4b (qisqa ID)
docker exec lab ip addr show eth0
docker inspect -f "{{.NetworkSettings.IPAddress}}" lab

4.Fayl tizimi (UFS / overlay2)

docker exec lab sh -c "echo salom > /salom.txt; rm /etc/nginx/conf.d/default.conf"
docker diff lab
# A /salom.txt                      ← qo'shildi (Added)
# C /etc/nginx/conf.d               ← o'zgardi (Changed)
# D /etc/nginx/conf.d/default.conf  ← o'chirildi (Deleted) = whiteout
sudo ls $(docker inspect -f "{{.GraphDriver.Data.UpperDir}}" lab)

5.Limitlar (cgroups)

docker stats --no-stream lab    # LIMIT ustunida 64MiB
docker exec lab cat /sys/fs/cgroup/memory.max   # 67108864
docker exec lab cat /sys/fs/cgroup/cpu.max      # 50000 100000

6.Metama'lumot va loglar

docker inspect lab | less        # to'liq JSON: Config, HostConfig, State, Mounts
docker logs lab                  # curl so'rovimiz ko'rinadi
sudo ls /var/lib/docker/containers/$(docker inspect -f "{{.Id}}" lab)/

7.Holatdan image yasash va tozalash

docker commit lab lab-image:v1  # R/W qatlam yangi image qatlamiga aylanadi
docker image history lab-image:v1
docker export lab -o lab.tar     # butun merged fayl tizimi bitta tar'da
docker rm -f lab && docker image rm lab-image:v1
Uy vazifasi: -m 10m bilan konteyner ochib, ichida katta fayl yaratib ko'r va exit kodini kuzat.

commit va export farqi:

  • commit → qatlamlar va tarix saqlanadi, natija image.
  • export → faqat fayllar, bitta tekis tar; tarix va Config yo'qoladi.
  • Ikkalasi ham faqat o'rganish uchun. Doimiy image'ni Dockerfile bilan yig'!

1.Konteynerlarni boshqarish

Konteynerning hayot sikli:

docker run -d -p 8080:80 --name proxy nginx   # fonda, port, nom bilan
docker run -it --rm alpine sh                  # interaktiv, chiqqach o'chadi
docker run -e MODE=production -v data:/app/data myapp
docker ps -a                     # barcha konteynerlar
docker logs -f proxy             # loglarni jonli kuzatish
docker exec -it proxy bash       # ishlab turgan konteyner ichiga kirish
docker stop proxy && docker rm proxy     # yoki: docker rm -f proxy
docker cp ./index.html proxy:/usr/share/nginx/html/
docker inspect proxy --format "{{ .NetworkSettings.IPAddress }}"
docker commit proxy myimage:v1   # konteyner holatidan image yasash

Boshqa foydali buyruqlar: top, stats, rename, restart, wait, port, diff, export/import, update.

2.Image va teglar

Image nomi: [registry/][foydalanuvchi/]nom[:teg]. Teg ko'rsatilmasa — :latest. Masalan alpine:3.9 va alpine:latest bir xil image bo'lishi mumkin (bir ID, ikki nom).

docker image pull nginx:1.16.0
docker image ls                         # REPOSITORY, TAG, IMAGE ID, CREATED, SIZE
docker image history nginx             # qaysi qatlamlardan tuzilgan
docker image tag nginx myname/nginx:v1
docker image push myname/nginx:v1
docker save -o nginx.tar nginx  /  docker load -i nginx.tar   # internetsiz ko'chirish
docker image prune                      # <none> "osilib qolgan" image'larni tozalash

alpine — atigi ≈5 MB'lik minimal Linux. Kichik image = tez yuklanadi, xavfsizroq.

3.Dockerfile

FROM nginx:1.16.0                       # asosiy image
LABEL version="1.0" maintainer="Lectrum LLC"
ENV WORKDIR /usr/share/nginx/html
WORKDIR ${WORKDIR}                      # ishchi papka
RUN apt-get update \
    && apt-get install curl -y \
    && ln -sf /dev/stdout /var/log/nginx/access.log
COPY index.html index.html
EXPOSE 80
HEALTHCHECK --interval=10s CMD curl -f localhost/ || exit 1
CMD ["nginx", "-g", "daemon off;"]

Yig'ish: docker build -t myname/site:1.0 .

Multi-stage build — bitta Dockerfile'da bir necha FROM. Birinchi bosqichda kod yig'iladi, yakuniy image'ga faqat natija ko'chiriladi. Image 1 GB'dan 30 MB'gacha kichrayishi mumkin:

FROM node:20 AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci                     # node_modules'ni COPY qilma, shu yerda o'rnat
COPY . .
RUN npm run build

FROM nginx:alpine
COPY --from=build /app/build /usr/share/nginx/html

.dockerignore faylida node_modules, .git kabilarni yoz — build tezlashadi.

4.Ma'lumot saqlash: volumes

Konteyner o'chsa, ichidagi yozilgan fayllar ham o'chadi. Ma'lumotni saqlab qolishning uch yo'li bor:

Volume

Docker o'zi boshqaradigan joy. Eng to'g'ri tanlov: ma'lumotlar bazasi, yuklangan fayllar.

-v nginx-vol:/usr/share/nginx/html

Bind mount

Host'dagi aniq papkani ulash. Ishlab chiqishda qulay: kodni o'zgartirsang, konteynerda darhol ko'rinadi.

-v $(pwd)/site:/usr/share/nginx/html

tmpfs

Faqat RAM'da, diskka yozilmaydi. Vaqtinchalik yoki maxfiy fayllar uchun.

--mount type=tmpfs,destination=/cache

docker volume create nginx-vol
docker run -d --mount source=nginx-vol,destination=/usr/share/nginx/html,readonly nginx:alpine
docker volume ls | inspect | rm | prune

5.Tarmoq (network)

Konteynerlar bir-biri bilan va tashqi dunyo bilan tarmoq orqali gaplashadi. Drayverlar:

  • bridge — standart. Bitta host ichidagi virtual «switch». O'zing yaratgan bridge'da konteynerlar bir-birini nomi bilan topadi (ichki DNS).
  • host — konteyner host tarmog'ini to'g'ridan-to'g'ri ishlatadi (izolyatsiyasiz, tezroq).
  • none — tarmoq umuman yo'q.
  • overlay — bir nechta serverdagi konteynerlarni bitta tarmoqqa bog'laydi (Swarm).
  • macvlan — konteynerga haqiqiy MAC manzil beradi, u tarmoqda alohida qurilmadek ko'rinadi.

Kursdagi fullstack misoli: proxy ikkala tarmoqda, db esa tashqaridan umuman ko'rinmaydi:

docker network create frontend              # standart driver: bridge
docker network connect frontend proxy
docker network inspect | ls | disconnect | rm | prune

6.Docker Compose

Ko'p konteynerli ilovani bitta YAML faylda tasvirlab, bitta buyruq bilan ko'tarish. Yuqoridagi sxemaning kodi (qisqartirilgan):

services:
  proxy:
    build: ./proxy
    ports: ["80:80"]
    depends_on:
      api: { condition: service_healthy }
    networks: [front, back]
  webhost:
    build: ./frontend-docker
    networks: [front]
  api:
    build: ./backend-docker
    environment: [PORT=4000, DB_URL=db, DB_NAME=customers]
    healthcheck:
      test: curl localhost:4000/api/ping
      interval: 10s
    networks: [back]
  db:
    image: mongo:4
    volumes: ["./data:/data/db"]
    networks: [back]
networks:
  front: {}
  back: {}
docker compose up -d --build    # hammasini yig'ib ko'tarish
docker compose ps | logs -f | exec api sh
docker compose down -v          # to'xtatish va volume'larni ham o'chirish

7.Registry va avtomatik build

  • Docker Hub: docker login → docker push. Rasmiy (official) image'lar: nginx, node, mongo, postgres…
  • O'z registry'ing: docker run -d -p 5000:5000 registry:2, keyin localhost:5000/myapp:1.0 ga push.
  • Avtomatik build: GitHub'ga push qilinganda image o'zi yig'iladi (Docker Hub Automated Builds, GitHub Actions).

Yaxshi amaliyotlar va xatolar

✓ Shunday qil

  • Bitta konteyner — bitta vazifa. Veb-server, API va baza alohida konteynerlarda.
  • Kichik asos: alpine, -slim, distroless.
  • Multi-stage build bilan kompilyatorlarni yakuniy image'dan olib tashla.
  • Teglarni aniq qo'y: node:20.11-alpine, latest emas.

✗ Bunday qilma

  • Konteyner ichiga SSH o'rnatish — buning uchun docker exec bor.
  • Ishlab turgan konteynerni qo'lda «tuzatish» — keyingi qayta ishga tushirishda hammasi yo'qoladi.
  • Ma'lumotlar bazasini volume'siz ishlatish.

  • apt-get updateni installdan alohida RUN'da yozish (eskirgan kesh xavfi).
  • Parollarni image ichiga yozish.

12-factor tamoyillaridan konteynerga oidlari

  1. Konfiguratsiya muhitda — bitta image dev, test va prod'da ishlaydi.
  2. Jarayonlar holatsiz — holat bazada yoki volume'da.
  3. Tez ishga tushish va toza to'xtash — SIGTERM'ni ushla.
  4. Loglar — hodisalar oqimi — stdout'ga yoz, yig'ishni tizim qiladi.
  5. Dev va prod o'xshash — compose bilan lokalda ham xuddi shu servislar.
Muammo bo'lsa tartib: docker ps -a → docker logs → docker inspect (State, ExitCode) → docker exec ichiga kirib tekshirish.

O'zingni tekshir

Avval o'zing javob ber, keyin savolni bosib to'g'ri javobni ko'r.

Konteyner va virtual mashinaning asosiy farqi nima?

VM apparat darajasida virtualizatsiya qiladi va har birida to'liq mehmon OT bor. Konteyner OT darajasida izolyatsiya qiladi va host yadrosini bo'lishadi, shuning uchun yengil va tez.

Image va konteyner o'rtasidagi bog'liqlik qanday?

Image — read-only shablon (sinf). Konteyner — undan yaratilgan, ustiga R/W qatlam qo'shilgan va ishlayotgan nusxa (ob'ekt). Bitta image'dan ko'p konteyner bo'ladi.

Konteyner izolyatsiyasini Linux yadrosining qaysi ikki mexanizmi ta'minlaydi?

Namespaces (nimani ko'radi) va cgroups (qancha resurs ishlatadi).

docker, dockerd, containerd va runc — kim nima qiladi?

docker — mijoz (CLI); dockerd — daemon, API'ni qabul qiladi; containerd — konteynerlar hayot siklini boshqaradi; runc — yadro bilan gaplashib jarayonni ishga tushiradi.

overlay2 da upperdir va lowerdir nima?

lowerdir — image qatlamlari (faqat o'qish). upperdir — konteynerning yoziladigan qatlami. merged — ikkalasining birlashgan ko'rinishi.

Nega RUN rm katta.zip image hajmini kamaytirmaydi?

Fayl oldingi qatlamda qoladi; yangi qatlam faqat «whiteout» bilan uni yashiradi. Yuklash va o'chirishni bitta RUN ichida qilish kerak.

Konteyner exit 137 bilan to'xtadi. Sababi nima bo'lishi mumkin?

137 = 128 + 9, ya'ni SIGKILL. Ko'pincha OOM (xotira limiti) yoki docker stop vaqti tugagani. .State.OOMKilled ni tekshir.

Nega CMD ["node","app.js"] ko'rinishi CMD node app.js dan yaxshi?

Exec formada node PID 1 bo'ladi va SIGTERM'ni oladi. Shell formada PID 1 = sh, u signalni uzatmaydi va konteyner 10 soniyadan keyin majburan o'ldiriladi.

-p 8080:80 da qaysi raqam host'niki?

Chapdagi — host (8080), o'ngdagi — konteyner (80). Ichkarida iptables DNAT qoidasi ishlaydi.

Nega standart bridge tarmog'ida konteynerlar bir-birini nomi bilan topolmaydi?

Ichki DNS (127.0.0.11) faqat foydalanuvchi yaratgan tarmoqlarda ishlaydi. docker network create bilan tarmoq yarat.

Volume, bind mount va tmpfs farqi?

Volume — Docker boshqaradigan joy; bind mount — host'dagi istalgan papka; tmpfs — faqat RAM'da, diskka yozilmaydi.

Nega docker.sock'ni konteynerga ulash xavfli?

Socket orqali Docker API'ga to'liq kirish mumkin, ya'ni --privileged konteyner ochib, host'ni boshqarish mumkin. Bu amalda host'da root huquqi.

Teg va digest farqi nima?

Teg o'zgaruvchan yorliq (:1.27), digest esa mazmunning sha256 xeshi va o'zgarmas.

docker run = qaysi ikki buyruq?

docker create + docker start (kerak bo'lsa oldin pull ham).
